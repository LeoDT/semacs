## 停止局限与 CPU 证据边界

当前普通 native probe 完成整个窗口的动作序列后，Python `read_report` 才检查预算，第一处异常是 open ready；此时改宽、换字体及其余首轮动作已采集。CSV 各动作 observed_elapsed_ms 合计约 55.397 秒，包含打开 / 改宽 / 换字体反复等待，并非只运行了一个约 20 秒的打开后立即停止。工具确实阻止后续窗口，但没有在当前窗口第一阶段超限时及时中止。

用户 CPU 升高观察应保留；本批只有墙钟 / draw / submit 计时，没有进程 CPU 采样、调用栈或 preparation sidecar。慢的主要可观察区间是完整布局就绪等待，而非持续大量前台 draw；现有数据不能区分 shaping / 缺字回退、换行计算、锁等待或调度，也不能量化 CPU 百分比。不能简单解释为一次正常字体加载，尤其同一进程的改宽再次接近 20 秒。

## 离线源码定位范围

静态核对显示 `RowScanner::validate_row` 对候选视觉行调用 `FontMeasure::shaped_width`，后者进入真实 GPUI shaping；测量用 WindowTextSystem 每 256 次请求重建，以保持缓存有界。mix 文本包含多脚本、emoji 和带编号的不同逻辑行，真实后端成本与轻量 TestTextSystem 并不等价。

这是后续应测量的热点候选，不是已证实根因。本地全目标测试和小样本真实字体正确性测试不能替代此原生 8 MiB 性能证据。尚未针对本次失败实施产品修复或诊断代码。

本批原生性能失败，E3 恢复为性能阻塞；此前人工功能复核通过仍有效，但不宣布全阶段完成，不进入 F，预算不变。中文输入轻微视觉跳动继续按用户意见暂不处理，不与此次大文件性能混为一因。
