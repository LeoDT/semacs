# E3 原生性能失败后的离线成本分解

## 范围与身份

接续 [原生 mixed 失败](e3-native-perf-host-01.md)。用户要求继续查看；本轮只运行独立的 release 离线探针，真实后端使用 `CosmicTextSystem::new_without_system_fonts`，只加载项目随包 Lilex 四变体。没有 Application / 窗口、系统字体数据库、用户配置、OS 注键或新的原生性能批次；没有改产品算法、依赖版本、失败 fixture 或预算。

HEAD 仍为 `138995b31a615833e04a729e8d619c829b9667c4`，产品为未提交 E3 / Lilex 修复状态，与原生失败时一致。探针经临时 crate 调用生产 `FontMeasure` / `WrapJob`，锁定 GPUI 依赖版本不变，源码为 `.pi/tmp/e3-font-fallback/wrap_cost.rs`，SHA-256 为 `87515d99ade3e44ac9910046644c4dfa013b58a9a1c411054a6e25633e9befe0`。诊断没有另调 reviewer；只读 explorer 核对的结论由主代理检查本地 Zed 实际源码后采用。

## 方法

包装 `PlatformTextSystem::layout_line`，统计实际 backend 调用数、输入字节数及内部墙钟；将单字素调用与整段调用分开。这里计数的是 GPUI 行布局缓存 miss 后的真实后端调用，不是所有测量请求。总时间覆盖生产完整 wrap 构建，shaping 时间为后端调用耗时之和，不能当作宿主 CPU 周期采样。

对同一份文本分别使用 Noop 与无系统字体的真实 Lilex 后端；宽度为 738 px，16 px / 24 px，普通字体。先做小规模诊断，再对三种约 2 MiB 文本各做三轮。ASCII 各字符由 Lilex 覆盖，不涉及系统字体回退；mixed 为失败样本的 2 MiB 前缀，但没有 CJK / emoji 字体，故它仅用于成本隔离，不能冒充宿主混排、缺字回退或字形正确性实验。

## 三轮结果

日志：`.pi/tmp/e3-font-fallback/wrap-cost-2m-r{1,2,3}.log`。

| 文本 | 字节数 | Noop 总耗时范围 | Lilex 总耗时范围 | Lilex 后端 shaping 耗时范围 | 实际后端调用数 |
|---|---:|---:|---:|---:|---:|
| 带不同编号的 ASCII 逻辑行 | 2,097,190 | 104.359–126.605 ms | 742.921–800.205 ms | 642.062–691.765 ms | 47,127 |
| 重复 ASCII 逻辑行 | 2,172,071 | 68.956–84.197 ms | 71.620–72.719 ms | 3.546–3.618 ms | 311 |
| mixed 前缀（缺少非拉丁回退字体） | 2,097,152 | 86.001–104.708 ms | 1,324.668–1,339.354 ms | 1,238.849–1,251.008 ms | 36,866 |

不同编号 ASCII 的 47,127 次调用中，只有 29 次为单字素测宽，合计仅 0.139–0.210 ms；主要成本是 47,098 次候选行上下文 shaping。三轮 Noop / Lilex 的行数均为 47,099，调用数也相同，便于在此 ASCII 情况下隔离后端成本。

重复文本与不同编号文本的长度 / 行内容不同，不作为严格单变量加速比；但它说明缓存能命中的重复布局与每行不同的布局有显著成本差别。不能把重复模板的快速结果外推为一般编辑文档性能。

## 已确认的热点与不能推断的部分

- 当前 `RowScanner::validate_row` 对每条候选视觉行做完整上下文 shaping，超宽时继续收缩并重测。`FontMeasure::shape_width` 的有界 GPUI 缓存无法消除大量不同正文行的实际 shaping。
- 在完全没有系统字体回退的纯 ASCII 实验中，真实后端 shaping 已占总成本约 86%。因此不能将本次问题全部归因于中文 / emoji 回退，也不能将所有成本当作一次字体加载。
- 这确认了生产全文索引策略的一个主要成本来源；没有逐项解释宿主 20.12 秒，也没有取得其 CPU 栈。真实宿主的缺字回退、锁等待等附加成本仍未分离。
- Noop 性能通过和小样本真实字体正确性通过，均不足以证明大文档真实字体性能。单纯扩大布局缓存会增加资源占用，且不能让不同文本的行互相命中，不能直接作为修复。

## Zed 源码对照与待确认取舍

主代理核对本地 Zed 快照 `ba63a022c9a22ca66d68ef2a8f0bb9b5b0a9984d`：

- `crates/editor/src/display_map/wrap_map.rs` 的后台更新将逻辑行交给 `LineWrapper::wrap_line`，没有对全文各候选视觉行执行 semacs 的完整 shaping 校验。
- `crates/gpui/src/text_system/line_wrapper.rs::width_for_char` 缓存 ASCII / 其他字符宽度，以 `TextSystem::layout_width` 的字符宽度计算换行候选；这是与逐候选行最终上下文 shaping 不同的策略。

**候选方案，尚未批准或实施**：让全文换行索引使用按有效字体 / 字重 / 斜体身份缓存的字素宽度，精确 shaping 留给实际可见绘制与输入几何，类似 Zed 的职责分工；不能退回所有变体共用一个固定等宽值，也不能使用估算几何处理 IME / 命中。

这意味着不再承诺任意字体、连字、复杂文字上下文下的换行断点与逐行精确排版完全相同。现有候选行精校和上下文回归体现了更严格选择，不能静默删除后宣称行为未变。需先与用户确认换行精度边界；若保留全文逐行精确约束，则要继续研究更复杂的排版 / 后端方案，本轮没有证明一个保持该约束且满足预算的简单修复。

普通 native probe 的逐阶段停止仍待实现：应在当前阶段的首份场景、完整 ready 或 draw 超限时保存部分报告并退出，不再自动推进改宽 / 字体等后续动作。该工具修复不构成性能问题本身已解决。

当前停在证据与方案确认，不关闭性能阻塞、不调宽预算、不进入 F；新真实环境运行仍另行授权。
